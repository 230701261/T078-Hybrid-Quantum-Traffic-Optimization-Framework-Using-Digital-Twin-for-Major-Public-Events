1. PROJECT OVERVIEW

Project name: Chepauk Traffic Digital Twin (source banner: SUMO + TraCI Traffic Simulation Digital Twin Engine).
Project type: Local web application for traffic simulation visualization, paired simulation comparison, optimization, and operator control.
Primary objective: Simulate the Chepauk study area with SUMO, expose simulation state and controls through a FastAPI service, visualize the network in a browser, and optionally request traffic optimization from a separate Quantum service or use a Classical fallback.
Use case: Demonstration and operator experimentation for normal-day/event-day traffic scenarios around the stadium, railway, and coastal study area.
Simulation: SUMO with two independent SUMO/TraCI contexts named Classical and Quantum.
Languages: Python, JavaScript, HTML, CSS, XML, JSON, PowerShell.
Backend: FastAPI, Uvicorn, Pydantic, SUMO TraCI/sumolib.
Frontend: Static HTML/CSS/JavaScript, Three.js, OrbitControls, Chart.js.
Optimization: The bundled Quantum module under quantum_module/Quantum-main contains the Python API, QUBO/QAOA and Classical solver. The integration client also has an in-process Classical fallback.
Scope note: Cloud/database persistence internals are excluded as requested. Their absence from this document does not imply that the source lacks them.

2. SYSTEM PURPOSE

The browser is the operator and visualization client. SUMO computes vehicle movement on a modeled road graph. TraCI lets Python control and observe running SUMO processes. The Digital Twin backend owns simulation lifecycle, reads current simulation state, exposes REST and WebSocket interfaces, validates operational changes, and returns telemetry. The optimization path converts live/requested traffic context into an optimization request, obtains a bitstring and action plan, maps the plan to canonical network IDs, validates it, applies supported actions, and reads back the resulting SUMO state.

The 3D Digital Twin is a visualization of the network geometry and simulation telemetry; it is not the traffic simulator. SUMO remains the source of vehicle motion. Classical optimization provides a deterministic solver and fallback path; the separate service attempts QAOA when configured. A computed plan is not itself proof that its actions were applied: the integration API records application status separately.

4. COMPLETE DATA FLOW

1. The browser loads the static UI served by FastAPI. It calls REST endpoints to initialize network geometry, status, controls, operator capabilities, scenario configuration, and history.
2. The user action is sent as an HTTP JSON body or query parameter. FastAPI validates basic shape/ranges and invokes the relevant manager/controller.
3. SimulationPair coordinates the Classical and Quantum TraCIController instances. Each controller owns a SUMO process/session and a worker loop that steps SUMO and builds snapshots.
4. Normal/Event scenario XML supplies network, demand, vehicle types/flows, stops and polygons. Scenario input code validates vehicle routes against actual network connectivity/classes; density changes generate a route-file variant rather than altering the network topology.
5. On optimization, server.py builds OptimizationRequest data from current simulation snapshots, current scenario and operator constraints. OptimizationJobManager invokes QuantumOptimizationClient.
6. The client requests the separate optimization API process. On HTTP failure it tries the bundled in-process Classical solver. The response is parsed as OptimizationResponse; a failed fallback is returned as failed status rather than a successful plan.
7. QuantumResultValidator checks bitstring shape; QuantumToTrafficMapper maps logical corridor/junction action names to project IDs and SUMO IDs. ConstraintEngine checks commands against live IDs, operation types, closures, and other supplied context.
8. TraCIAdapter applies supported commands under a shared TraCI lock, records prior state where implemented, reads back effects and rolls back a failed batch where implemented. Operator control endpoints use SimulationPair and its own paired transaction logic.
9. SUMO advances; TraCI snapshots include time, vehicles, pedestrians, edges, traffic lights, and demand/runtime counts. Python sanitizes values for JSON and broadcasts a stream to connected WebSocket clients.
10. The browser updates metrics, maps, controls, events, charts and camera targets. Three.js maps SUMO coordinates using a shared transform; it does not create the live vehicles.

Protocols/data: REST uses JSON (FastAPI/Pydantic models or dictionaries); WebSocket is /ws/simulation and sends JSON snapshots; Quantum HTTP uses JSON at /api/quantum/optimize and health at /health (service implementation is bundled, but launched separately). Exact error details vary by endpoint; FastAPI returns HTTP errors, operational events are kept in process memory, and controller snapshots expose status/error fields.

7. QUANTUM MODULE

The Quantum API and optimizer are now included under quantum_module/Quantum-main. python/integration/quantum_client.py prefers the bundled source for its in-process Classical fallback and retains the previous sibling-checkout path as a compatibility fallback. The API still runs as a separate process, expected at 127.0.0.1:8001. Its live health was NOT ESTABLISHED here.

Integration API request: OptimizationRequest contains message_id, simulation_id, scenario_id, timestamp, schema_version and payload. Payload includes optional event metadata, constraints, live intersection load mapping, solver, density, route modifications and signal timings. Response: run/message/simulation/scenario identifiers, solver label, 18-character binary string, corridor/signal/restriction actions, benefit fields, objective, runtime, status, application result, applied flag and optional error.

The bundled Quantum source contains dynamic variable construction, QUBO/problem builders, a QAOA solver using Qiskit primitives and Aer statevector simulation, and a Classical optimizer. The current source code (not a live process) uses an 18-bit model: four route-diversion bits, ten signal-extension bits, four restriction bits. The QAOA search code uses one ansatz layer and an 8-by-8 parameter grid with 512 shots per point; it uses the most frequent measured string and decoder/repair logic. The Classical solver enumerates candidate binary assignments (2^18 possible combinations) and evaluates the objective under constraints. Those are source details, not measured runtime values.

The integration client sends an HTTP POST to /api/quantum/optimize. It does not expose all HTTP errors to the operator before attempting fallback. Offline fallback invokes the bundled Classical optimizer with isolated temporary artifacts, checks that generated solver/plan/export files share the bitstring, and returns applied_to_sumo=false. It does not itself mutate SUMO. The job manager then validates/maps/applies if configured. Schema bitstring validation accepts only 18 binary characters. Unknown result IDs are rejected by ID mapping. A duplicate message/run path is handled by job manager idempotency checks. Exact behavior for every unknown optimization ID is endpoint-dependent; do not infer broader persistence guarantees.

QAOA is a simulator-based optimization path in this project, not execution on physical quantum hardware. API health and live quantum service availability require a separate running process and are NOT VERIFIED in this documentation.

8. QUANTUM DECISION VARIABLES

Variable positions are generated from the bundled corridor/junction configuration. The current adapter and validator define positional groups as follows; exact display-name-to-canonical-SUMO mapping comes from python/integration/id_mapper.py and bundled JSON data.

| Bit positions | Meaning | Type | Source/consumer | Potential output |
| 0–3 | Four corridor diversion decisions, ordered from configured corridor list | binary | decision_variables.py; QUBO builder; decoder; mapper | route/corridor priority actions |
| 4–13 | Ten configured junction signal extension decisions | binary | junction mapping; QUBO/decoder; adapter | TLS phase-duration change |
| 14–17 | Four corridor restriction decisions | binary | corridor config; QUBO/decoder; adapter | configured speed restriction |

The source groups impose/recommend limits of at most two diversions, five signal extensions, and one restriction. Adapter validation prints warnings for exceeding group counts; it does not itself reject solely on those counts. ConstraintEngine and live target validation provide additional gates. Per-variable output effect depends on decoded plan fields and mappings. The full named order is configuration insertion order, not inferred here as a universal invariant; the exact external config may change it.

9. SUMO MODULE

SUMO is an external executable/library runtime. python/traci_controller.py launches SUMO with the scenario config, connects via TraCI, runs simulation steps on a worker, extracts snapshots and closes the process/connection. Two controllers have distinct labels and sessions. Step length is 0.5 simulation seconds as configured in python/config.py. Each scenario config references the same network and additionals but its own route demand. The network is prebuilt (network.net.xml), with source node/edge/type/connection files retained. Scenario route files define traffic flows/vehicles and route distribution. Startup route preflight parses route definitions against the network, checks edge continuity and vehicle class permission before Uvicorn/SUMO startup.

The simulation loop advances SUMO using TraCI simulationStep, maintains running/pause state and captures vehicle/person/edge/TLS data. Reset/restart closes and starts new simulation processes through controller/pair methods. Exact SUMO binary resolution is environment-dependent through TraCI/SUMO_HOME/PATH; no installed SUMO version was inspected for this documentation.

11. TRACI MODULE

TraCIController owns one named SUMO process/connection. traci_session provides serialized session access using a lock; traci_controller.start launches SUMO and initializes connection/network caches. The simulation loop steps the connected process and calls _extract_snapshot. Snapshots include simulation clock, active/pending/completed demand counts as available from TraCI, vehicles with id/type/edge/route/position/speed/angle, pedestrians/persons, traffic lights and edge congestion/queue measures.

Network methods enumerate routes, edges and signals. Routing uses NetworkRoutingService plus SUMO network/routing queries; route mutation calls TraCI vehicle.setRoute after connectivity/class/closure validation, reads route back and checks destination/active state. Edge closure saves prior lane permissions, changes allowed classes, reads back, and supports restore. Signal timing discovers current programs/phases/state/duration/next switch and can set a phase duration subject to configured and program limits. Paired SimulationPair operations snapshot each context, validate both, apply, compare readback and attempt rollback. Connection errors surface into operation failures/status; reconnect behavior beyond restart/recreate methods is NOT ESTABLISHED. No TraCI/SUMO runtime was started for this documentation.

13. CLASSICAL OPTIMIZATION

There are two related Classical paths. The bundled Classical optimizer solves the same QUBO by enumerating binary candidates; it can be requested as a solver or used as the client's offline fallback. That fallback returns a validated OptimizationResponse and plan, with applied_to_sumo=false. The separate existing fallback in the Quantum API is bundled in this repository. Solver complexity and optimization result depend on the model/input; source does not establish performance at operational scale. The runtime measured objective and duration are not documented because no run was performed. A solver response is mapped through QuantumToTrafficMapper and ConstraintEngine before optional TraCI application.

14. CONSTRAINT ENGINE

File: python/integration/constraint_engine.py; class ConstraintEngine. Main entry points: validate_command, validate_batch, validate_commands and edge_is_closed. It checks supported command types, command parameter validity, live edge/TLS/vehicle IDs when context supplies them, canonical/logical target consistency, route/closure and operation conflicts, and batch conflicts. QuantumToTrafficMapper validates logical IDs before constructing DigitalTwinCommand; TraCIAdapter calls validate_batch before first mutation. Operator routes/signals/closures have both API and SimulationPair/controller prechecks; not every operator code path necessarily invokes the same shared method, so “all operator mutations pass through one universal engine” is not established. Invalid batches return structured validation errors and apply zero commands at the adapter boundary. Paired mutation failures trigger snapshot rollback where snapshots exist.

15. ROUTE OPERATIONS

Corridor registry: python/integration/id_mapper.py; live corridor discovery is combined with controller route metadata by /api/network/routes and exposed through /api/operator/capabilities. Alternative corridors are filtered for distinctness/connectivity. POST /api/operator/route-operation validates requested corridor pair/share, configured duration and block flag, captures Classical and Quantum route snapshots, calls SimulationPair.apply_operator_route_operation, reports eligible/rerouted counts and actual share per context, destination preservation and readback status, and activates expiry only after success. RouteRoutingService validates current edge, route, class/permissions/connectivity, destination and affected flow/vehicle state.

Block-new-entry is not an unconditional blanket closure: the operation checks active/future dependencies and may reject when loaded flows/vehicles rely on those edges. Scheduled flow diversion is explicitly advertised unavailable in capabilities. Clear and expiration call restore_operator_route_operation using the saved snapshots; successful state is reported after readback. Failure can yield rollback/rejected/restore error. Expiry uses backend time and emits operation events. No operation was run during documentation.

16. SIGNAL TIMING

Discovery is based on TraCI network_signals() and active programs in both controllers. Capability response intersects safely supported RED/GREEN state options and duration ranges across paired contexts; mappings are derived from actual phase-state strings rather than fixed phase numbers. UI reads these capabilities and current live values. POST /api/operator/signal-timing delegates to SimulationPair.apply_operator_signal_timing; the pair validates both sides, applies supported phase duration, reads current phase/state/duration/next switch and restores the prior snapshot if one side fails. Configuration includes broad operator safety bounds; SUMO phase values are the runtime source. Fixed phases are not independently editable. GREEN/RED availability depends on discovered phase strings and runtime capability.

17. OPERATING CONSTRAINTS

Weather profile values and descriptions are from python/operator_profiles.json. It applies speed factors and can restore baseline/prior values; it is a simulated traffic profile, not actual weather sensing. Construction supports profile mode (speed cap/travel-time factor) and conditional closure mode (lane permission change). Profile and closure are separate timer records with restore state. VIP corridor preference changes route costs and expires; VIP entity assignment is explicitly unavailable because no matching VIP demand entity/type is defined. All states are exposed by capabilities/state API and recorded in events. Behavior is subject to live controller availability, constraints and readback.

18. ROUTE EXPLAINABILITY

23. COORDINATE SYSTEM

SUMO network coordinates are local x/y from the compiled net; the exporter also reads netOffset. In this network, +X is east and +Y is north. Three.js uses +X east, +Y vertical elevation, and -Z north. `worldToSceneCoordinates(sumoX, sumoY, elevation)` returns THREE.Vector3(sumoX, elevation, -sumoY). The exporter shifts additional polygon coordinates by SUMO netOffset to align with the compiled network. Roads, nodes, crossing shapes, 3D elevated lane shapes, stops, landmarks, vehicles, labels and camera focus are intended to use this shared transform. The `shapeCoordinates` helper accounts for Three.js extruded-shape axis orientation. No extra global geographic projection, scale factor, or rotation is applied in this transform; network coordinates provide scene scale. This documents source implementation, not a renewed geographic-accuracy audit.

29. STARTUP / RUN PROCEDURE

Prerequisites: Windows or compatible Python environment; Python packages from requirements.txt; SUMO and its TraCI/sumolib Python modules available to the interpreter; network/scenario XML present; bundled Quantum module for optimization, or app’s in-process Classical fallback for offline optimization.

From project root in PowerShell:
    python -m venv .venv
    .\.venv\Scripts\Activate.ps1
    python -m pip install -r requirements.txt
    python -m python.main

The project also supports `python python\main.py` per source comment. Startup checks port 8000, validates both scenario route files before starting SUMO, and runs one Digital Twin Uvicorn server. Browser opens at http://127.0.0.1:8000. Keep the terminal open; Ctrl+C triggers Uvicorn shutdown hooks.

Quantum service (separate process): the application expects an API at http://127.0.0.1:8001 by default. From repository root, activate the project environment, run Set-Location quantum_module/Quantum-main, then python -m uvicorn api.main:app --host 127.0.0.1 --port 8001. Check http://127.0.0.1:8001/health. Install quantum_module/Quantum-main/requirements.txt in the shared environment. If the service is unavailable, the client attempts an in-process Classical fallback.

Safe project restart: from project root run `./restart_digital_twin.ps1` in PowerShell. It confirms the listener is this project, requests POST /api/control/shutdown, waits for release and runs current source. It refuses arbitrary port owners and never terminates unrelated processes. Select normal_day/event_day in the UI or via API after startup. Do not run another Digital Twin listener on the same port.

WebSocket state: set of connected socket objects in server process.

37. ERROR HANDLING

Startup route errors are caught before server bind and reported as ROUTE_INVALID. Port conflicts are detected; unrelated process is not killed. FastAPI validates query constraints and uses HTTPException for invalid/unsupported operations. Route and signal paired operations report rejected/rolled-back/partial outcomes. TraCI failures cause operation error and rollback attempts; rollback failure is represented as partial/restoration error where the caller detects it. Quantum client catches HTTP failure and invokes Classical fallback; fallback failure returns failed response. Adapter validation failure prevents batch writes. JSON-safe conversion handles non-finite values. Frontend exception and disconnect behavior is source-dependent; browser console/runtime was not inspected for this documentation.

38. SAFETY / VALIDATION

Confirmed mechanisms: pre-start route continuity/class permission checks; Pydantic response/bitstring validation; operator input range and dynamic target checks; route connectivity and vehicle class checks; ConstraintEngine batch gate before optimizer TraCI writes; live edge/TLS ID checks; closure preflight against current vehicles and loaded demand; saved-state snapshots for supported reversible operations; paired context validation and rollback; readback before APPLIED; expiry restoration callback; startup duplicate-port refusal; graceful shutdown script that verifies project identity. Limitations: process crashes can interrupt in-memory rollback/timers; universal ConstraintEngine coverage across every low-level endpoint is not established; readback is only as complete as each operation’s verification logic.

- SUMO installation/version, current server PID/state, current Quantum API health and current browser are not inspected here.

41. 5-MINUTE PROJECT UNDERSTANDING

1. SUMO owns vehicle movement on the provided Chepauk road graph and normal/event demand files.
2. Python starts two SUMO instances and controls both with TraCI.
3. FastAPI at 127.0.0.1:8000 exposes simulation control, state, network geometry and operator APIs.
4. The browser receives geometry and live snapshots, then draws them with Three.js.
5. Optimization sends live context to a separate Quantum API at 8001; if unavailable, the client can invoke a local Classical solver.
6. Optimizer plans only affect SUMO after mapping, validation and application; supported operations read back and may roll back.
